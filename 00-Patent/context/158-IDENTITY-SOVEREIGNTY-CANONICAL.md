## 0. Purpose

This document captures the full design of Reckon's multi-user identity-sovereignty architecture. It extends the existing single-tenant cryptographic spine (docs/90, docs/95, docs/145) to a multi-user model where:

- A **USER** is a first-class actor with the same standing as agents in the mission DAG
- **Zero private-key material** ever exists on vendor infrastructure — for any actor, human or agent
- The **derivation path IS the chain of authority** — verifiable from any COC entry without a database lookup
- **Sovereignty and governance are cleanly separated** — the operator can freeze/preserve/legal-hold storage without ever being able to read ciphertext or forge a signature

The design is a direct extension of Claim 7d ("zero vendor-side cryptographic surface") into the multi-user, multi-agent identity plane.

## 1. Three-Tier Identity Hierarchy

All identity material derives from a single **user master seed** — a random 256-bit secret that never leaves the user's device and is never transmitted to or generated by vendor infrastructure.

```
USER MASTER SEED  (never server-seen; lives only on client devices)
├── m/0        →  PERSONAL HUMAN KEY   (Ed25519)
├── m/agent/0  →  AGENT KEY: agent-0   (Ed25519, spawned for this user)
├── m/agent/1  →  AGENT KEY: agent-1   (Ed25519, spawned for this user)
├── m/agent/N  →  AGENT KEY: agent-N   (Ed25519, spawned for this user)
└── m/dek      →  DATA-ENCRYPTION KEY  (symmetric; encrypts forensics → B2)
```

### 1.1 Personal Human Key — `m/0`

- **Algorithm:** Ed25519 (SLIP-0010 derivation path `m/0`)
- **Scope:** Signs authority events — charter counter-seals, agent-delegation acceptances, two-parent federation merges
- **Semantics:** The f(0) "one act a human is responsible for." Human signs once to accept a charter; all agent work under that charter is cryptographically chained to this root acceptance
- **Server role:** Holds public key only. Verifies signatures. Never generates or holds private key.

### 1.2 Agent Keys — `m/agent/N`

- **Algorithm:** Ed25519 (SLIP-0010 derivation path `m/agent/N`)
- **Scope:** Signs manifests and COC entries on behalf of the spawning user
- **Derivation:** Computed client-side at spawn time. The agent receives its private key in the spawn bundle; uses it to sign artifacts during its run; discards it when the session ends.
- **Chain of authority:** The derivation path `m/agent/N` is cryptographically provable from the agent's public key to the user's master seed (via SLIP-0010 HD derivation). Any verifier can confirm "this agent acted under user X" directly from the COC entry — no database lookup, no trust in the vendor's identity store.
- **Replaces:** The current `5e_agent_sign.py init` server-side key generation flow (see §5 Build Order)

### 1.3 Data-Encryption Key — `m/dek`

- **Algorithm:** Symmetric (e.g., XChaCha20-Poly1305 or AES-256-GCM), derived via SLIP-0010 `m/dek`
- **Scope:** Encrypts all forensics/data written to B2 object storage before upload
- **Server role:** Holds ciphertext only. The server is architecturally incapable of reading stored data without the user's DEK.
- **Existing:** This tier is the subject of Claim 7 / Claim 7d (already filed in provisional). The innovation in this document is extending the derivation model so the DEK is derived from the same master seed as the human and agent keys.

## 3. Recovery Architecture (SLIP-0039)

The master seed must survive device loss without the vendor ever holding a reconstruction-capable share.

### 3.1 Shamir's Secret Sharing via SLIP-0039

SLIP-0039 (Shamir's Secret Sharing for Mnemonic codes) splits the master seed into **n mnemonic shares** where any **k-of-n** shares reconstruct the seed. Below k shares: information-theoretically zero. Reconstructed material is indistinguishable from random.

**Default policy: 2-of-3**

| Share | Holder | Storage |
|-------|--------|---------|
| Share 1 | User primary | Hardware wallet / password manager |
| Share 2 | User backup | Separate secure location |
| Share 3 | Operator-held (optional) | Encrypted under operator master; ALWAYS < k |

### 3.2 The Operator Share Constraint

The operator ALWAYS holds fewer than k shares. With the default 2-of-3 policy, the operator holds at most 1 share.

**Consequence:** The operator can NEVER reconstruct the master seed unilaterally — not even under subpoena, legal process, or internal breach. This is an arithmetic property of Shamir's scheme, not a policy commitment.

If a government presents a court order demanding user data, the operator can:
- Produce the ciphertext stored in B2 (operator holds write/read on the bucket)
- Produce the operator's single Shamir share
- **Cannot** produce the decryption key (requires k=2 shares; operator has 1)

SLIP-0039 group/member thresholds support richer policies (e.g., 3-of-5 with corporate escrow groups) for enterprise deployments.

### 3.3 Recovery Ceremony (Client-Side)

The recovery ceremony is client-side-only:

```
1. Gather k mnemonic shares (from separate secure locations)
2. Feed to SLIP-0039 combiner → reconstructed master seed (in-memory only)
3. Re-derive all keys via SLIP-0010 (human key, agent keys, DEK)
4. Re-provision: upload public keys to server; re-encrypt DEK-wrapped B2 access keys
5. Securely discard the assembled seed from memory
```

No vendor involvement. No network calls during the seed-reconstruction phase.

## 4. Sovereignty vs. Governance Separation

This architecture cleanly separates two concerns that are often conflated:

| Layer | Operator Capability | Operator Limit |
|-------|---------------------|----------------|
| **Seed / Data layer** (Shamir + DEK) | Holds < k shares | Cannot reconstruct seed; cannot decrypt data |
| **Storage layer** (B2 application keys) | Holds master/governance key for bucket | Can FREEZE / PRESERVE / LEGAL-HOLD the bucket |
| **Signing layer** (Ed25519 private keys) | Holds public keys only | Cannot forge signatures or impersonate user |

### 4.1 Legal-Hold Without Read-Access

When the operator exercises their governance B2 key (e.g., for a legal hold):

- The bucket is locked: agents cannot write, delete, or overwrite
- The content is preserved exactly as stored
- The content remains entirely ciphertext from the operator's perspective
- The operator can testify: "we preserved all data; here is the hash chain; we cannot read it"

This satisfies a "freeze and preserve" court order while maintaining the user's data sovereignty. The operator's compliance posture and the user's privacy are not in conflict — they operate on different layers.

### 4.2 B2 Key Wrapping [UNBUILT]

The user's three B2 application keys (write-only for agents, read-only for user, master/governance for operator) are wrapped under the user's human key (`m/0`). The wrapped keys are stored in `~/.b2/provisioning-registry.json` and decoded only by the client that holds the private key.

Currently the registry tracks key IDs only; secrets live in the user's environment. The full wrapping scheme described here (keys wrapped under `m/0`) is architectural design pending implementation.

## 5. Federation: Human Keys as Signing Branches

Multi-user collaboration uses the same acceptance ritual that agents already use for charter co-signatures (docs/145), extended to human keys.

**Cross-user merge:** User A's human key (`m/0`) signs a **two-parent merge** (Claim 12) of User B's mission-branch root into User A's mission DAG. This is identical to an agent co-signing a charter — except the signing key is a human key derived at `m/0`.

```
User A Mission DAG              User B Mission DAG
        │                               │
   branch-root-A                  branch-root-B
        │                               │
        └─────── two-parent merge ──────┘
                        │
              signed by: User A m/0 key
              verifies:  User A accepted User B's work
                        │
               merged-branch-root
```

**Property:** Any verifier can confirm "User A accepted User B's branch" from the signature on the merge manifest — using the same SLIP-0010 derivation chain that proves agent keys. No separate identity system. No vendor-mediated trust.

## 6. What Changes in Existing Infrastructure

### 6.1 `scripts/5e_agent_sign.py` — Migration Required [UNBUILT]

**Current behavior:**
- `init` command: generates agent keypair on the server (`forensics/reputation/keys/{agent_type}.key`)
- Server holds private keys; agents read them at sign time

**Target behavior after migration:**
- Server: verify-only (holds `{agent_type}.pub` only)
- `init` command becomes `register-pub`: accepts an externally-derived public key, writes only the `.pub` file
- Agent spawn bundles include the client-derived private key (derived `m/agent/N` → passed to agent via secure channel)
- Private keys never touch server disk; agent discards key after session

**Backward compat note:** All existing `.pub` files and signatures remain valid. The migration only changes WHERE new keys are generated; existing signatures verify unchanged.

### 6.2 `forensics/reputation/keys/` [PARTIAL MIGRATION]

Current state: contains both `.pub` and `.key` files (server-generated). After migration: contains only `.pub` files. The `.key` files become inert legacy that can be safely rotated out on next key rotation.

### 6.3 `~/.b2/provisioning-registry.json` [UNBUILT]

After the B2 key-wrapping sprint: the registry gains a `wrapped_keys` section where each user's B2 application key IDs are stored with their secrets encrypted under the user's `m/0` public key. Unwrapping requires the client to hold the `m/0` private key.

## 7. Build Order

The architecture is layered. Each step is independently deliverable and does not require completing later steps to be useful.

### Step 1 — Library Selection (prerequisite for all later steps)

Choose an HD derivation library supporting SLIP-0010 with Ed25519:

| Library | Language | SLIP-0010 | SLIP-0039 | Ed25519 | Notes |
|---------|----------|-----------|-----------|---------|-------|
| `slip10` (Python) | Python 3 | Full | No | Ed25519 confirmed | Minimal; needs companion for SLIP-0039 |
| `emip3` | Python 3 | Full | No | Ed25519 confirmed | Cardano ecosystem provenance |
| `mnemonic` + `shamir-mnemonic` | Python 3 | No | Full (Trezor ref impl) | via companion | Trezor's SLIP-0039 reference |
| `python-slip10` | Python 3 | Full | No | Ed25519 confirmed | Most actively maintained |
| `@scure/slip10` | TypeScript | Full | No | Ed25519 confirmed | Best for browser/client |

**Recommended pair:** `python-slip10` + `shamir-mnemonic` (Trezor reference implementation). Both are pure-Python, audited, and Ed25519-compatible. The Trezor `shamir-mnemonic` is the SLIP-0039 reference — most likely to stay specification-conformant.

**Flag:** Verify `python-slip10` Ed25519 support produces keys compatible with `pynacl` (what `5e_agent_sign.py` uses). Both use the standard Ed25519 encoding; compatibility expected but must be tested.

### Step 2 — SLIP-0039 Recovery Ceremony (standalone utility)

Deliver: `scripts/identity/recovery_ceremony.py`

```
Functions:
  generate_master_seed() → bytes (256-bit CSPRNG)
  split_seed(seed, n, k) → list[str]  (SLIP-0039 shares as mnemonics)
  reconstruct_seed(shares: list[str]) → bytes
  verify_round_trip(seed) → bool
```

This has zero server-side footprint. Can be developed and tested entirely client-side. No changes to existing infra required.

### Step 3 — SLIP-0010 Key Derivation (standalone utility)

Deliver: `scripts/identity/key_derivation.py`

```
Functions:
  derive_human_key(seed) → (sk_bytes, pk_bytes)   # m/0
  derive_agent_key(seed, n) → (sk_bytes, pk_bytes) # m/agent/N
  derive_dek(seed) → bytes                          # m/dek
  public_fingerprint(pk_bytes) → str               # matches 5e_agent_sign.fingerprint() format
```

Compatibility target: `public_fingerprint()` output must match `5e_agent_sign.fingerprint()` format (`{agent_type}-{keyfp8}`) so existing manifest filenames remain valid.

### Step 4 — `5e_agent_sign.py` Migration to Verify-Only

**Changes to `5e_agent_sign.py`:**

1. Add `register-pub <agent_type> <pubkey_hex>` command: writes `.pub` file from externally-provided public key bytes. Does NOT generate a `.key` file.
2. Deprecate `init` (or keep as dev-only mode gated behind `RECKON_ALLOW_SERVER_KEYGEN=1`)
3. Server spawn bundles gain `agent_private_key_b64` field (client-derived `m/agent/N`); `5e_agent_sign.sign()` can accept key material inline rather than reading from disk

**What does NOT change:** `sign()`, `verify()`, `fingerprint()`, `cosign_charter()`, `counterseal_charter()`, `verify_seal()` — all unmodified. The signing primitives are algorithm-agnostic.

### Step 5 — Recovery Ceremony Integration

Wire `recovery_ceremony.py` into the client-side onboarding flow. Steps:

1. At first login: `generate_master_seed()` → display 3 SLIP-0039 shares to user
2. User stores shares 1+2; optionally sends share 3 to operator endpoint (encrypted under operator public key)
3. Public keys derived from seed uploaded to server via `register-pub`
4. Master seed discarded from browser memory after key registration

### Step 6 — B2 Key Wrapping (deepest sovereignty layer)

After Steps 1-5 are live, the B2 provisioning flow gains key-wrapping:

1. At provisioning, generate B2 application keys as now
2. Encrypt each key under user's `m/0` public key (NaCl box / X25519 hybrid)
3. Store wrapped ciphertexts in `~/.b2/provisioning-registry.json` under `wrapped_keys`
4. Unwrap client-side only (requires `m/0` private key)

**What changes in `~/.b2/provisioning-registry.json`:** Add `wrapped_keys` section. Existing `key_ids` section unchanged.

## 9. Prior Art Notes (for patent review)

The novelty of this architecture relative to existing HD wallet and key management art lies in the **mission-DAG integration**:

- **BIP-32/SLIP-0010 in cryptocurrency:** HD key derivation is standard in the crypto wallet space. The novelty here is using the derivation PATH as the chain-of-authority in an AI-agent forensic system — agents are children of the human root, and this relationship is verifiable from any COC entry without a lookup table.
- **SLIP-0039 (Trezor):** The Shamir recovery scheme is existing art. The novelty is the operator-always-less-than-k constraint combined with storage-layer governance (freeze-without-read) as a compliance architecture.
- **AWS KMS / Azure Key Vault / HashiCorp Vault:** Distinguished by zero vendor private-key surface (Claim 7d). In CMK/BYOK patterns the vendor operates key management infrastructure and retains computational access. In this design no private key is ever generated by or stored on vendor infrastructure.
- **Closest prior art concern:** BIP-32 wallets with multisig — but these do not address AI-agent forensic chains of custody, mission DAG integration, or the compliance posture (sovereignty/governance separation).
